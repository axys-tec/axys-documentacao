# Arquivamento de Tenant — Interface Hub ↔ Easy

**Status:** Descritivo para o time do Hub (v0)
**Data:** 2026-06-14
**Escopo:** ciclo de **desconstrução** e **reconstrução** dos dados operacionais de um tenant
no AxysEasy (módulo Ativo). Documento de **fronteira**: descreve o que o Easy faz e o que o
**Hub precisa decidir e documentar do lado dele**.

---

## 1. Problema

Em uso recorrente, o Easy acumula orçamentos/ativos por tenant. Tenant que **parou de pagar
licença** (ou comprou uso único e não voltou) não pode manter dados no **banco quente**: é
barato para 1, inviável para milhões. A solução é tirar do quente, guardar de forma recuperável
e devolver se o tenant voltar.

Evolui o backup R2 já aprovado para um **ciclo por-tenant dirigido pelo Hub**.

---

## 2. Fronteira de responsabilidade (essencial)

> **O Hub manda; o Easy executa.** O Easy **NÃO conhece a regra** de licença/inatividade.
> Ele expõe duas operações e as executa **quando o Hub chama**.

| Responsabilidade | Dono |
|---|---|
| Estado de licença do tenant (ativa/inativa, desde quando) | **Hub** |
| Política de inatividade: quantos dias sem licença disparam arquivamento (variável) | **Hub** |
| Tabela de limites/parâmetros do ciclo (N dias, janela de varredura) | **Hub** |
| Cadência da varredura (ex.: a cada 30 dias) | **Hub** |
| Decidir QUANDO desconstruir / reconstruir / purgar | **Hub** |
| Cobrança na reconstrução | **Hub** |
| Executar a desconstrução (extrair + arquivar + limpar o quente) | **Easy** |
| Executar a reconstrução (recarregar no quente) | **Easy** |
| Guardar o payload e o registro do arquivamento | **Easy** |

O time do Hub deve **documentar do seu lado** a política (regra dos N dias, cadência, gatilhos,
cobrança). O Easy só recebe a ordem.

---

## 3. Operações que o Easy expõe

Ambas **assíncronas** (Celery): a chamada do Hub agenda a tarefa e recebe um id de
acompanhamento; o resultado é consultável depois.

### 3.1 `desconstruir(tenant_uuid)`
1. Lê **todas as tabelas do tenant** (recorte determinístico — ver §4).
2. Gera um **backfill JSON estruturado** (mesmos nomes de tabela/coluna do banco).
3. Grava o payload no destino (**R2 catalogado** ou schema frio).
4. Registra em `arquivo.arquivamentos` (onde está, hash, contagens, validade).
5. **DELETE** dos registros do tenant no banco quente.

Idempotente: tenant já `ARQUIVADO` não re-arquiva.

### 3.2 `reconstruir(tenant_uuid)`
1. Localiza o arquivamento ativo do tenant.
2. Recarrega o backfill no banco quente **preservando os IDs originais** (as PKs do Easy são
   `GENERATED BY DEFAULT`, então o reinsert mantém as relações/FKs intactas).
3. Marca o registro como `RESTAURADO`.

> A **cobrança** da reconstrução é do Hub e acontece **antes** de chamar o Easy.

---

## 4. O que entra no arquivamento (escopo de dados)

Recorte **por tenant** é determinístico por design do schema do Easy:
- `tenant_uuid` existe só nas **raízes** (`ativo.empreendimentos`, `ativo.ativos`,
  `tenant_catalogo.*`); todas as folhas penduram por **FK**.
- Logo, o footprint do tenant = essas raízes `WHERE tenant_uuid = X` + todos os descendentes
  por FK.

**Fica de fora (nunca arquivado):** o schema `catalogo` (SINAPI, CDHU, preços, documentos) é
**global e compartilhado** — não pertence a tenant nenhum.

---

## 5. Registro (o "catálogo no SQL"): `arquivo.arquivamentos`

O payload em si vai para o R2 (ou schema frio); o **índice consultável** fica em SQL:

| Campo | Função |
|---|---|
| `arq_tenant_uuid` | tenant arquivado |
| `arq_status` | `ARQUIVADO` / `RESTAURADO` / `PURGADO` |
| `arq_destino` | `R2` / `SCHEMA_FRIO` |
| `arq_localizacao` | path no R2 (ou nome do schema frio) |
| `arq_payload_hash` | checksum do backfill (integridade) |
| `arq_tabelas_json` | `{ "ativo.ativos": 12, "ativo.ativo_itens": 3480, … }` (banco × qtd) |
| `arq_arquivado_em` / `arq_restaurado_em` | datas |
| `arq_expira_em` | `arquivado_em + 5 anos` (alvo de purga) |

---

## 6. Retenção

- Payloads guardados por **~5 anos** (`arq_expira_em`).
- Não voltou no prazo → **purga** (apaga o payload e marca `PURGADO`).
- **O gatilho da purga também é do Hub** (o Easy só executa).

---

## 7. Estados

```
(quente)  --desconstruir-->  ARQUIVADO  --reconstruir-->  RESTAURADO (quente)
                                  |
                                  | (passou 5 anos, Hub manda purgar)
                                  v
                               PURGADO
```

---

## 8. O que o time do Hub precisa definir/documentar

1. **Política de inatividade**: N dias sem licença para arquivar (e onde fica essa variável).
2. **Cadência** da varredura e como o Hub seleciona os tenants elegíveis.
3. **Contrato de chamada** Hub→Easy: endpoint/fila, autenticação, payload mínimo
   (`tenant_uuid`, operação), e como o Hub consulta o status da tarefa.
4. **Cobrança** na reconstrução (gate antes de chamar o Easy).
5. **Gatilho de purga** aos 5 anos.
6. **Confirmação do destino** padrão (R2 vs schema frio) — recomendação do Easy: **R2 catalogado**.

> Quando o Hub fechar esses pontos, o Easy implementa o `ArquivamentoService`
> (`desconstruir`/`reconstruir`) e a tarefa Celery contra esta interface.

---

## Cross-ref: graça pós-contrato (licenciamento)

O gatilho da **desconstrução** respeita a **garantia de persistência** definida em
`EASY_HUB_LICENCIAMENTO.md` §5: **30 dias garantidos** no banco quente após o fim do contrato
(**prática: 90 dias**), durante os quais o tenant fica em **VIEW_ONLY** (vê/baixa RASCUNHO, não
produz) e **NÃO** vai para backup. Só após esse N (decisão do Hub, ≥30) a desconstrução leva ao
backup e o status vira **ARCHIVED**.
